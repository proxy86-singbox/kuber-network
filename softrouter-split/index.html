回国分流策略：哪些流量该走专线，哪些必须留本地

软路由软路由分流P1更新于 2026-11-05

两个原因。第一，专线带宽有限，几十兆的专线塞满全屋流量，晚高峰一定卡。第二，很多流量本来就是本地的，视频会议、本地流媒体、系统更新，这些走本地又快又不占专线。分流的目的是把有限的高质量带宽留给真正需要的场景。

视频制作中

三张表怎么定

分三类。第一类必走专线：国内电商后台、国内社交平台的管理端、国内的支付和银行、国内的直播推流。第二类走本地：本地的视频网站、系统更新、软件下载、云盘同步。第三类看情况：游戏和视频通话，看你对延迟和抖动的敏感度。

三张表先列出来，再往设备上写规则。

域名分流还是地址分流

域名分流的优点是精准，缺点是维护成本，平台换个域名你可能就漏了。地址分流的优点是稳定，缺点是颗粒度粗，一个网段里可能混着你要和不要的地址。实际做法是以域名为主、地址为辅，主力平台用域名规则，补充规则用地址段，两条并行。

游戏 UDP 要单独处理

游戏走的是 UDP，规则里如果只按域名和 TCP 端口匹配，游戏流量会漏掉。表现就是网页能开，游戏还在用本地线路，延迟三百多。处理办法是把游戏的服务端地址段也加进规则，或者干脆把游戏设备的全部流量打标走专线。

设备级的分流比应用级省事。

分流错了的表现

几个典型表现。网页打不开但 ping 得通，说明域名解析没跟着线路走。能开网页但视频一直转圈，说明视频的 CDN 域名没命中规则。登录后台总是要验证，说明你的出口地址在两条线路之间来回切，这种情况最危险，一定要把规则做互斥。

规则要互斥

最后一条原则，规则互斥。同一个目标地址，不能出现两个规则都命中、优先级不同的情况。流量一会儿走这条一会儿走那条，平台看到的是 IP 在跳，这比固定在一个不干净的 IP 上还糟。写完规则之后，把规则列表按顺序看一遍，确认没有重叠。

规则冲突怎么排查

分流规则写多了最容易出现「互相覆盖」。表现是：某个域名明明写了走专线，实际却直连；或者国内站点莫名变慢。排查方法是从路由决策链的末端往前看：

# 1. 看这个目标实际走哪条路由
ip route get 8.8.8.8
ip route get www.baidu.com

# 2. 看 mangle 标记有没有打上
nft list ruleset | grep -A5 mark
# 或（老版本）
iptables -t mangle -L -n -v | grep -i mark

# 3. 看 ipset 里到底有没有这个网段
nft list set inet fw4 cn_direct

顺序判断法：如果第 3 步的集合里没有这个目标，问题在填充规则；如果有但路由不对，问题在标记；标记对但路由不对，问题在路由表优先级。

ipset / nftset 与 dnsmasq 的配合

按域名分流的实现依赖「解析时把结果写进集合」：

# dnsmasq
ipset=/youtube.com/google.com/proxy-set
nftset=/openai.com/4#inet#fw4#proxy-set

# nftables 侧
set proxy-set { type ipv4_addr; flags interval; }

两个关键细节：

  1. `flags interval` 让集合能存网段而不只是单地址，否则一次解析出多个 A 记录会占满集合
  2. 集合需要定时清理（`timeout` 属性），否则客户端切换 CDN 节点后会留下大量过期条目，路由表膨胀

分流的性能开销

按域名分流的成本主要在 DNS 解析与集合维护，不在转发。实测口径（普通 x86 软路由）：

分流方式转发开销首包延迟增加内存占用
按目的地址（地址库）极低0-1ms小
按域名（dnsmasq + nftset）低1-5ms（首次解析）中
按进程（客户端 TUN）中2-8ms大

所以「全屋设备 + 按域名分流」是可以做到的，代价是首次访问某域名时的解析稍慢（之后走缓存）。

一份验证清单

  • 国内主流站点 5 个：直连，`curl -s ipip.net` 回显本地 IP
  • 境外主流站点 5 个：走隧道，回显隧道 IP
  • 游戏或语音：UDP 能通（用 `nc -u` 或直接跑一次语音）
  • DNS：dnsleaktest 结果与 IP 同区域
  • 断线：拔掉主 WAN，30 秒内是否按预期回退或切换

一份对照表：症状 → 层 → 处理

分流出问题时的判断，最好按层来做，而不是一上来就改规则：

症状出问题的层验证方法处理
全部流量走隧道路由（默认路由被抢）`ip route` 看默认路由关 defaultroute
全部流量直连标记或 rule 未生效`nft list ruleset` 看 mark检查 rule 优先级
个别站走错集合未填充`nft list set` 看条目检查 dnsmasq 的 nftset 行
时好时坏规则冲突或缓存重复测试同一目标清理集合与缓存
UDP 不通分流只处理了 TCP`nc -u` 测 UDP补 UDP 规则或改 TUN

按这张表走，绝大多数分流问题三步内能定位。真正的难点不是配置语法，而是「知道该看哪一层」。

一个十行的分流验收脚本

#!/usr/bin/env bash
ok=0; bad=0
check() {  # $1=域名 $2=期望出口(本地|隧道)
  local ip; ip=$(curl -s --max-time 8 "https://$1/" >/dev/null 2>&1 && echo ok)
  [ "$ip" = "ok" ] && ok=$((ok+1)) || bad=$((bad+1))
}
for d in www.baidu.com www.qq.com www.taobao.com; do check "$d"; done
echo "可达 $ok / 失败 $bad"

更严格的版本会让每个域名实际回显出口 IP 再比对，但十行版本的价值是「一秒钟跑完、结果一眼可见」，适合每次改规则后立刻执行。

一个判断「规则是否过时」的习惯

每隔一段时间做一次「关掉规则测试」：临时把分流规则停用，用直连访问几个常用境外站。如果直连也能打开，说明这些规则可以精简；如果打不开，说明规则还在起作用。规则只增不减，最后会变成没人敢动的黑盒。
