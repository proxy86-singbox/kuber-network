MTU 和分片：网页打得开但图片加载不出来是怎么回事

排障MTU分片P2更新于 2026-11-05

MTU 是一个数据包最大能有多大，以太网默认是一五零零字节。走隧道的时候，外层要加包头，可用空间就少了几十字节。隧道两端的 MTU 如果没对齐，大包过不去，就会被丢弃或者分片。这就是为什么小请求能通、大文件不通。

视频制作中

典型症状清单

对照这几条。网页文字能显示，图片加载一半卡住。能登录，但上传附件失败。能打开首页，点进详情页白屏。ping 得通，网页打不开。这些症状的共同点是小包通过、大包丢失。符合这个特征，基本可以判定是 MTU。

怎么测出合适的值

用 ping 的分片禁止参数测。从一四七二开始，每次减八，目标是你落地端的网关。哪一次开始能通，那个值加上二十八个字节的头，就是你的可用 MTU。常见的结果是一四零零到一四五零之间。

实测出来再填，别照抄别人的数字。

改哪几个地方

要改的地方可能有三处。隧道接口本身的 MTU，局域网网卡的 MTU，还有路由器上的分片修正设置。三处对齐了才有效。只改一处，包在转发的某一跳还是会被丢。改完清一下连接状态，让新连接用新的值。

改完怎么验

验三件事。第一，之前打不开的图片页面现在能不能完整加载。第二，上传一个大文件试试，能不能一次成功。第三，连续访问十分钟，看有没有间歇性卡顿。三件都过，说明改对了。如果只有一部分改善，说明还有一处没对齐。

别把 MTU 当万能药

提醒一下。MTU 不匹配的症状很典型，但不要把所有的时通时不通都归到 MTU 上。丢包、DNS 解析失败、连接数超限，症状都可能类似。先用 ping 测出结果，确认了再改。没测就改，改完你会更混乱。

探测路径 MTU 的正确方法

Linux/macOS 的 ping 带 DF 标志（不分片），从大往小试，第一个不通的下一个值就是上限：

# Linux
for s in 1472 1450 1420 1400 1380 1360; do
  if ping -c 2 -M do -s $s 目标 >/dev/null 2>&1; then
    echo "MTU $((s+28)) 可用"; break
  fi
done
# macOS（-D 是 DF 标志，-s 是载荷大小）
for s in 1472 1450 1420 1400 1380; do
  ping -c 2 -D -s $s 目标 >/dev/null 2>&1 && echo "MTU $((s+28)) 可用" && break
done

`+28` 是 IP 头（20）与 ICMP 头（8）。算出来的就是该路径可用 MTU。

链路建议 MTU/MRU备注

MSS Clamping 比调 MTU 更省事

MTU 是两端的约定，MSS 是 TCP 层告诉对端「我最多收多大的段」。开启 MSS clamping 后，路由器会自动把 MSS 改小，不必逐台设备调整 MTU：

# OpenWrt / iptables
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu

iKuai 里对应的选项是 WAN 设置里的「MSS 自动调整」。这一项开启之后，「网页打得开但图片加载不出来」这类问题基本消失。

改完怎么验

三个层次依次验：

  1. 大包能过：`ping -M do -s 1400 目标` 成功
  2. TCP 能传大文件：`curl -o /dev/null -r 0-52428800 大文件URL` 不中断且速度稳定
  3. 网页完整加载：图片、视频、字体都出来，不卡在某一类资源

三个都过，说明 MTU 与 MSS 都对了。只过第一个不算——ICMP 和 TCP 的路径行为可能不同。

别把 MTU 当万能药

以下现象容易误诊为 MTU 问题，其实不是：

现象更可能的原因
所有网页都慢线路质量或 DNS
只有某站慢该站的 CDN 或回源
视频卡但网页正常该站的视频节点问题
需要刷新才加载缓存或 DNS 解析时序

MTU 问题的特征是「与包大小相关」：小请求正常、大请求失败。不满足这个特征，先查别处。

分片问题的三个层次

MTU 相关的故障其实分三层，处理方式不同：

层现象处理
路径 MTU 小于两端约定大包丢失，传输中断调小 MTU
中间设备丢弃 ICMP 需分片PMTUD 失效，黑洞开 MSS clamp
应用层自己分片错误只有某应用出问题改应用配置，不是网络

第三层最容易被误判。比如某些老的 FTP 客户端在被动模式下不遵守协商的 MTU，导致传输卡住——这时候改路由器 MTU 没用，要改客户端设置。判别方法：换一个客户端做同样的事，如果正常，问题在应用层。

验证是否真的修好

改完 MTU 后不要只看「能打开网页」，要做能压出大包的动作：下载一个 50MB 以上的文件、打开一个高清图集、看一段 1080p 视频。这三件事都能触发大包传输，任何一件卡住就说明还没修好。

各设备上改 MTU 的位置

设备位置备注
iKuai网络设置 → WAN → 高级 → MTU/MSS同时开 MSS 自动调整
OpenWrt`/etc/config/network` 的 `option mtu`配合防火墙 `mtu_fix`
MikroTik`/interface l2tp-client set mtu=1400 mru=1400`需同时改 mru
macOS系统设置 → 网络 → 高级 → 硬件 → MTU一般选「自定义 1400」
iOS不可调（随客户端）客户端内有 MTU 选项的用它
Windows`netsh interface ipv4 set subinterface "以太网" mtu=1400 store=persistent`需管理员

优先在路由器上调，一次生效、全屋受益。逐台设备调只在「无法改路由器」时才考虑。

一个常被问的问题

「为什么同样的 MTU，有的网站正常有的不行？」因为不同服务端的 TCP 实现与中间路径不同：有的服务端会做 PMTUD 并正确响应 ICMP 需分片，有的直接把 ICMP 丢掉，形成黑洞。这正是 MSS clamping 存在的意义——它不依赖 ICMP，直接从 TCP 层把段改小。

一个经验值

如果你的链路是「家庭宽带 → 软路由 L2TP → 境外」，MTU 1400 几乎总是安全的。往上试 1420 有用但收益微小，往下到 1360 会牺牲约 3% 的吞吐。所以不用精细调，1400 + MSS clamp 覆盖九成场景。

一个完整的最小排障流程

遇到「网页打得开但图片、视频加载不出来」时，按四步走：第一步，用手机热点复测，排除固网出口的问题；第二步，把 MTU 设成 1400 并开启 MSS clamping；第三步，清浏览器缓存、系统 DNS 缓存与客户端缓存；第四步，用一个 50MB 以上的大文件下载验证是否稳定不中断。

四步之内能解决九成问题。剩下那成通常是目标站点侧或 CDN 侧的问题——判别方法很简单：换一个完全不同位置的站点做同样的大文件下载，如果那个站点也卡，才轮到怀疑自己的链路；如果只有某一个站点卡，问题在那个站点，不在你的网络。这个判别能避免大量无效的自我排查，也能避免向服务商提出无法验证的投诉。
