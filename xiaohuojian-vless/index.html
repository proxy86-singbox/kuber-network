Shadowrocket 小火箭配置 VLESS：参数怎么填，三个常见错误

代理协议小火箭VLESS配置P0更新于 2026-11-05

这期讲小火箭配 VLESS。现在主流两种配法，VLESS 加 TCP 加 TLS，和 VLESS 加 WS 加 TLS。前者性能好，后者伪装性强。看你网络环境选。

参数清单

手动添加的话，参数是这样。类型选 VLESS。地址填服务商给的域名或者IP。端口，TLS 一般是四百四十三。UUID 填服务商提供的那串。传输选 WS 或者 TCP。TLS 开启，SNI 填域名。

如果选 WS，路径填服务商给的路径，一般带斜杠。

错误一 端口和TLS不匹配

第一个常见错误，端口填八十但开了 TLS。八十是明文HTTP端口，TLS 走四百四十三。这两个配错，直接连不上，而且不会给你明确报错，就是一直转圈。

错误二 SNI不一致

第二个错误，SNI 和地址不一致。SNI 是 TLS 握手时告诉服务器你要访问哪个域名。如果地址填IP但SNI填域名，或者反过来，TLS 握手就会失败。原则是，SNI 必须和证书上的域名一致。

错误三 路径少了斜杠

第三个错误，WS 路径少了开头的斜杠。服务商给的是斜杠 abc，你填成 abc，少一个斜杠，服务器返回四百零三。这个错误特别隐蔽，因为小火箭里看起来填对了。

验证方法

配好之后先做延迟测试，不通就检查这三项。通了再看能不能打开网页。如果延迟通但网页打不开，多半是分流规则问题，把规则改成全局试试。

VLESS 是什么，为什么现在主流

VLESS 是 Xray 项目里的无状态传输协议，本质是「把一段加密的 TCP 流伪装成正常的 TLS 流量」。它不自己做加密（加密交给 TLS），只负责把目标地址、UUID 这类元信息打包进一个极简的头部，因此开销比 VMess 更低，握手更快。

三种主流组合，选哪种取决于你所在网络的管理强度：

组合特征适用网络性能
VLESS + TCP + TLS纯 TLS 长连接一般网络最好
VLESS + WS + TLS走 WebSocket，可套 CDN需要 CDN 中转、需要伪装成网站稍差
VLESS + Reality借用真实网站的 TLS 指纹，不需要自己的证书管理严格的网络好

字段填什么说明

错误一：端口与 TLS 状态不匹配

表现：一直转圈，最终提示连接超时，没有任何错误详情。

原因有两种：开了 TLS 但端口填 80，或者关了 TLS 但端口填 443。80 是明文 HTTP 端口，绝大部分服务端不在这个端口上跑 TLS，握手直接失败；443 上关掉 TLS 则服务端期待 TLS 握手而客户端发的是明文，同样失败。

正确对应关系：

  1. 443 → TLS 开
  2. 80 → TLS 关（仅当服务端确实在 80 上跑明文，少见）
  3. 自定义高端口 → 看服务端配置，不要猜

错误二：SNI 与地址不一致

表现：能握手但立刻断开，或者握手成功但访问任何网站都失败。

SNI（Server Name Indication）是 TLS 握手时客户端告诉服务器「我要访问哪个域名」的字段。服务端用 SNI 来选择证书。SNI 与证书域名不一致，握手会失败或被中间设备标记。

规则很硬：

  • 地址填域名时，SNI 可以是同一个域名，也可以留空（客户端会默认使用地址）
  • 地址填 IP 但服务端用的是域名证书时，SNI 必须显式填那个域名
  • 地址填 CDN 域名时，SNI 填 CDN 的域名

一个常见的错误做法是「SNI 随便填个大站的域名」，这在 Reality 场景里有意义，在普通 TLS 场景里必然失败，因为服务端出示的证书对不上。

错误三：WS 路径少了开头的斜杠

表现：延迟测试可能显示通（TCP 能建连），但打开网页返回 403 或 404。

服务端配置的路径是 `/abc`，客户端填成 `abc`，请求的 URI 就变成 `/abcabc` 或者干脆是非法 URI，服务端直接拒绝。

这个错误难发现，是因为小火箭的输入框看起来「填对了」，肉眼很难区分 `abc` 和 `/abc`。建议直接从服务商的分享链接导入，而不是手抄参数——手抄出错的概率比想象中高得多。

排查时可以直接在浏览器里验证：

# 应该返回 400/426 之类的协议层错误，而不是 404
curl -I "https://你的域名/你的路径"

返回 404 说明路径不对（服务端没这个 location）；返回 400 或 426 说明路径对上了，只是缺少 WebSocket 升级头，这是正常的。

分流规则怎么配

小火箭配置成功后，默认是全局代理，所有流量都走。这在日常使用里既浪费带宽又拖慢国内访问。正确做法是按规则分流。

规则类型写法示例用途
DOMAIN-SUFFIXDOMAIN-SUFFIX,google.com,PROXY按域名后缀
DOMAIN-KEYWORDDOMAIN-KEYWORD,youtube,PROXY按关键词
IP-CIDRIP-CIDR,8.8.8.8/32,PROXY按 IP 段
GEOIPGEOIP,CN,DIRECT国内 IP 直连
FINALFINAL,PROXY兜底

推荐顺序是：先把需要代理的域名和 IP 段列出来放前面，再加 GEOIP,CN,DIRECT 兜底直连，最后 FINAL,PROXY。顺序错了会出现「国内网站也走代理」或者「需要的站点没走代理」。

验证流程

配好之后按这个顺序验，能快速定位问题层：

  1. 延迟测试：小火箭里点节点做测试，通说明 TCP 可达
  2. 网页测试：打开一个境外站点，能开说明 TLS 与路径都对
  3. IP 回显：访问 IP 查询站点，显示的出口是不是节点 IP
  4. DNS 泄漏：检查 DNS 是否与出口同区域
  5. 分流测试：同时打开一个国内站点和一个境外站点，看是否各自直连/走代理

延迟通但网页打不开，八成是分流规则或 DNS 问题；延迟不通，八成是端口/TLS/路径三选一。

三个补充细节

  • UDP 转发：部分服务端不开 UDP，表现为游戏、语音、QUIC 不可用。客户端里把 UDP 关掉反而更稳，避免 QUIC 走代理失败后回退慢。
  • 订阅更新：用订阅链接而不是手抄，服务商换 IP 时自动同步。订阅链接本身要定期检查是否失效。
  • 电量与耗电：iOS 上长时间挂代理会显著耗电，按需开启（用快捷指令做场景化开关）比常驻更实际。

和 Clash / v2rayN 的差异

参数逻辑完全一样，差别在客户端实现：小火箭的优势是 iOS 上规则引擎成熟、支持脚本；Clash 系优势是规则生态与多平台统一；v2rayN 优势是 Windows 上调试信息全。三个客户端用同一个节点，效果应当一致——如果只有一个不通，问题在客户端配置而不是节点。

Reality 和普通 TLS 的差别

普通 TLS 的问题是：证书由你自己签发或申请，中间设备只要看到「一个不知名域名的证书」，就能据此做判定。Reality 的做法是不自己签证书，而是借用真实大站的 TLS 握手特征——客户端连你，握手过程却看起来像在访问那个真实站点。

配置要点三条：

  1. 服务端的 `dest` 指向一个真实的、支持 TLS 1.3 的站点（且该站点在你所在网络可访问）
  2. 客户端的 SNI 填那个真实站点的域名，fingerprint 与 dest 的实际 TLS 指纹一致（chrome 通常够用）
  3. 不要同时开 WS——Reality 与 WS 的组合既没有收益，还增加失败点

Reality 的代价是配置容错低：`dest` 选了一个握手特征不匹配的站点，表现是「能连上但立刻断」，且日志里不会有明显错误。

返回码速查

排查时先看返回码，能少走很多弯路：

现象含义处理
403路径对不上，或服务端拒绝了该 URI检查 WS 路径，注意开头斜杠
404服务端没有这个 location路径或域名错
426 Upgrade Required路径对了，缺 WebSocket 升级头客户端问题，不是服务端问题
连上即断TLS 握手完成但应用层被拒UUID 错，或 flow 配置不匹配
一直转圈TCP 都连不上端口、防火墙、IP 不可达

常见问题

小火箭的 VLESS 节点可以手动添加吗？

可以，但建议用分享链接或订阅导入。手动添加要填七项（类型、地址、端口、UUID、传输、TLS、SNI/路径），任何一项偏差都会导致连接失败且没有明确报错。手抄时最容易错的是 UUID 的大小写和 WS 路径开头的斜杠。

为什么延迟测试通过，但网页打不开？

延迟测试只验证 TCP 可达，不验证 TLS 与业务路径。网页打不开但延迟通，按顺序查：SNI 是否与证书域名一致、WS 路径是否正确、分流规则是否把这个域名分到了直连、DNS 是否解析异常。四项里 SNI 与路径错最常见。

VLESS 需要开 UDP 吗？

看用途。需要语音、游戏、QUIC 加速时开；只浏览网页时可以关。部分服务端不提供 UDP 转发，客户端开着会导致 QUIC 请求失败后回退变慢，表现为「打开网页有半秒卡顿」。不确定时先关，需要时再开。

SNI 到底该填什么？

填服务端证书上的域名。地址填域名时可以不填（客户端默认用地址）；地址填 IP 时必填，否则握手会因证书域名不匹配而失败。填一个无关的大站域名在普通 TLS 场景下一定失败，那种玩法属于 Reality 的用法，不要混用。

WS 和 TCP 两种传输怎么选？

能直连 443 且不需要 CDN 时选 TCP，性能更好。需要套 CDN（隐藏真实 IP、抗封锁）或服务端只提供 WS 时选 WS。WS 的代价是多一层帧封装，吞吐略低，但穿透性更强。

订阅链接失效了怎么办？

先判断是订阅地址失效还是节点失效：用浏览器打开订阅链接，能返回 base64 或配置文本说明订阅正常，问题在节点；返回 404/403 说明订阅地址变了，找服务商要新的。不要因为订阅失效就重置客户端，那会丢掉本地分流规则。

小火箭的分流规则会拖慢速度吗？

规则匹配的开销很小，通常不影响速度。真正影响速度的是「规则没命中导致走了错误路径」——比如国内站点被分到代理，绕一圈香港再回来。优化方向是让 GEOIP,CN,DIRECT 生效，而不是减少规则数量。

iOS 上挂代理很耗电，有办法缓解吗？

有。用快捷指令做场景化开关（例如只在打开特定 App 时开启），比常驻省电很多。另外关闭不必要的 UDP 转发、减少规则数量、避免使用脚本型规则，都能降低常驻开销。

同一个节点，手机能用、电脑不能用，为什么？

问题在客户端配置而不是节点。常见差异：电脑客户端的 TLS 设置（是否允许不安全证书、是否启用 uTLS）、系统时间偏差（TLS 对时间敏感，偏差超过几分钟会握手失败）、系统代理是否真的生效（部分软件不走系统代理）。

VLESS 和 Trojan 怎么选？

两者都是「伪装成 HTTPS」的思路。VLESS 的优势是无状态、开销低、可与 Reality 组合，生态更活跃；Trojan 的优势是配置简单、兼容性好。新部署优先 VLESS，已有 Trojan 稳定运行的不必迁移。
