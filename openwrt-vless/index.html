OpenWrt 上跑 VLESS：客户端参数和透明代理模式怎么选

代理协议OpenWrtVLESSP2更新于 2026-11-05

TUN 模式是在系统里建一个虚拟网卡，所有流量从这张网卡走，内核层面接管，兼容性最好。透明代理是拦 TCP 和 UDP 的连接，重定向到本地代理端口，资源占用低一些，但对某些特殊协议的处理不如 TUN 干净。软路由上如果设备多、流量杂，优先选 TUN。

视频制作中

必填的参数

必填的就五项。服务端地址、端口、用户标识那串字符、加密方式选无、传输层选 TCP 或者 WS。如果开了 TLS，还要填 SNI 和目标域名。WS 模式再加路径。这五项之外的都是可选项，别为了看着专业去乱开，开错一项反而连不上。

流控参数要不要开

流控这个参数，服务端支持才开，服务端不支持你开了也协商不上。表现是握手成功但立刻断开，日志里会有一行协商失败的提示。不确定的话先关掉，通了再试。它带来的收益主要是减少一次往返，实际体验差别不大。

路由规则怎么写

规则分两类。一类是直连，本地地址段、私有地址段、还有你确定不需要走专线的域名，都放直连。另一类是代理，需要走专线的平台域名放这里。规则匹配是从上到下，所以具体的规则要在前面，宽泛的规则在后面。

写反了，宽泛规则会先把流量吃掉。

怎么判断生效了

三个检查点。一，看进程状态，客户端在跑不等于规则生效。二，在设备上访问一个应该走专线的地址，同时在软路由上看客户端的连接数有没有增加。三，查出口地址是不是落地端的。三个都对，才是真的生效。

只看进程状态是最常见的误判。

和 L2TP 怎么共存

如果两个协议都要用，建议分设备而不是分流量。一台设备固定走 L2TP，另一台固定走 VLESS，规则简单不容易打架。同一台设备上让两种协议按域名切，出问题的时候你很难判断是哪一层的事，排查成本高很多。

TUN 模式和透明代理（redirect/tproxy）的选择

模式实现优点缺点适用
TUN建一张虚拟网卡接管路由全协议（含 UDP）透明，配置直观多占一点 CPU，需正确设置路由表全屋透明代理
redirect (nat)iptables/nftables 改写目标开销最小只处理 TCP，UDP 需额外处理只跑网页
tproxy透明代理套接字TCP+UDP 都能接管，不改目标地址配置复杂，需打 mark 与策略路由游戏/语音场景

家庭场景推荐 TUN：配置少、UDP 天然支持、排障直观（`ip route` 能看到默认路由指向 tun0）。

关键配置片段（sing-box / TUN）

{
  "inbounds": [{
    "type": "tun",
    "interface_name": "tun0",
    "inet4_address": "172.19.0.1/30",
    "auto_route": true,
    "strict_route": true,
    "sniff": true,
    "stack": "gvisor"
  }],
  "outbounds": [
    { "type": "vless", "tag": "proxy", "server": "你的域名", "server_port": 443,
      "uuid": "你的UUID", "tls": { "enabled": true, "server_name": "你的域名" } },
    { "type": "direct", "tag": "direct" }
  ],
  "route": {
    "rules": [
      { "protocol": "dns", "outbound": "direct" },
      { "ip_cidr": ["10.0.0.0/8", "192.168.0.0/16"], "outbound": "direct" },
      { "domain_suffix": [".cn"], "outbound": "direct" }
    ],
    "final": "proxy",
    "auto_detect_interface": true
  }
}

三个参数值得单独说：

  1. `strict_route`：防止应用绕过 TUN（部分应用会绑定物理网卡），开启后更彻底
  2. `sniff`：按 SNI/域名分流的前提，不开启就只能按 IP 判断
  3. `auto_detect_interface`：避免「代理自己连不上代理服务器」的经典死循环

和 L2TP 共存

两个出口同时存在时，要明确哪一个是默认。推荐做法：L2TP 作为「按目标」的出口（策略路由），VLESS 的 TUN 只接管「需要代理的域名」，两者互不抢默认路由。

冲突的典型表现是：开了 TUN 之后 L2TP 的流量也被卷进 TUN，形成「隧道套隧道」，延迟翻倍、MTU 二次缩水。判断方法是 `ip route` 看默认路由有几条、优先级如何；修法是把 L2TP 的对端地址加入 TUN 的绕过列表（在 route 规则里对服务器 IP 走 direct）。

DNS 劫持：TUN 模式下最容易漏的一步

TUN 接管了 IP 流量，但 DNS 请求往往是明文 UDP 53，如果不劫持，会出现「域名解析走本地、连接走代理」的错位：解析到国内 CDN 的节点，却用境外出口去连，速度极差甚至不通。

劫持配置（nftables）：

nft add table inet dns_hijack
nft add chain inet dns_hijack prerouting '{ type nat hook prerouting priority dstnat; }'
# 把所有去往 53 端口的请求转到本机 DNS
nft add rule inet dns_hijack prerouting udp dport 53 redirect to :53
nft add rule inet dns_hijack prerouting tcp dport 53 redirect to :53

配合 sing-box 的 `{"protocol":"dns","outbound":"proxy"}` 规则，就能做到「DNS 也走代理」。验证方法：`tcpdump -i any port 53` 看是否有明文 DNS 出到公网——有，说明劫持没生效。

开机自启与进程守护

TUN 模式依赖一个常驻进程，进程挂了整屋断网。用 systemd 托管并设置自动重启：

# /etc/systemd/system/sing-box.service
[Unit]
Description=sing-box
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/bin/sing-box run -c /etc/sing-box/config.json
Restart=always
RestartSec=5
LimitNOFILE=1048576

[Install]
WantedBy=multi-user.target
systemctl daemon-reload
systemctl enable --now sing-box
systemctl status sing-box | head -5

三个细节决定稳定性：`Restart=always` 保证崩溃后自愈；`RestartSec=5` 避免疯狂重启打满日志；`LimitNOFILE` 调大，否则高并发连接会撞到文件描述符上限（表现是「用一会儿就连不上」）。

三种常见故障

现象原因处理
开机后要手动重启服务才有网启动顺序早于网络就绪加 `network-online.target` 依赖
运行几小时后失效文件描述符耗尽调高 `LimitNOFILE`
部分应用完全不走代理`strict_route` 未开或应用绑定物理网卡开启 strict_route

与 L2TP 共存的推荐拓扑

最稳的分工是：L2TP 负责「不需要精细控制」的全屋设备（电视盒子、智能音箱、iPad），TUN 模式负责「需要按域名分流」的设备（电脑、手机）。两者共用同一条回国线路时，要确保 L2TP 的对端地址在 TUN 的直连列表里，否则隧道流量会被 TUN 二次接走。

验证方法：开两个窗口，一个持续 ping 隧道对端，另一个在 TUN 里下载大文件。对端 ping 不应出现明显抖动；如果抖动剧烈，说明流量被 TUN 卷进去了。

一个上线检查表

  • 服务 `enabled` 且 `active (running)`
  • `ip route` 里能看到 tun0 的默认路由，且优先级低于直连规则
  • 国内站点回显本地 IP，境外站点回显节点 IP
  • DNS 请求不出现在明文抓包里
  • 重启设备后自动恢复，无需人工干预

五项全过，才算「配好了」。只过前两项的人，通常会在某天重启后发现自己整屋断网。
